# 과제 목표 회고 — 무엇을 만들었고, 왜 그렇게 만들었나

이 문서는 과제 목표 6가지를 **JobFit 의 실제 코드와 실제 배포 경험에 근거해** 설명한다.
설명만으로 끝나지 않고, "이 파일의 이 함수가 이 역할을 한다"는 지점까지 파일명으로 연결하고,
마지막 항목에서는 실제로 겪고 고친 문제를 그대로 기록한다.

- 서비스: https://jobfit-seven.vercel.app
- 저장소: https://github.com/sayknow/A1-3
- 배포 형태: Vercel Serverless Functions (Python) + 정적 HTML/CSS/JS
- 문서 작성 시점의 실측: 공고 135건(Arbeitnow 60 / RemoteOK 59 / Remotive 16), AI 경로 3종(`ok`/`failed`/`disabled`) 모두 확인

## 1. HTML / CSS / JavaScript 는 각각 무슨 일을 하는가

### 한 문장 요약

| 파일 | 역할 | 이 프로젝트에서의 실제 예 |
| --- | --- | --- |
| **HTML** | 화면의 **구조와 의미**를 정한다. 데이터가 아니라 뼈대 | `public/recommend.html` 의 `<form id="recommend-form">` |
| **CSS** | 구조에 **모양과 배치, 반응형**을 입힌다 | `public/css/style.css` (478줄, 4개 페이지 공유) |
| **JavaScript** | **사용자 동작과 서버 통신, 화면 갱신**을 담당한다 | `public/js/recommend.js` 의 `handleSubmit()` |

### HTML — 무엇을 담는가

HTML은 "무엇이 화면에 있는가"를 선언한다. 이 프로젝트에서 HTML이 맡은 일은 세 가지다.

1. **페이지 골격과 내비게이션** — `index.html` / `recommend.html` / `jobs.html` / `about.html` 4개 페이지가 각각 `.nav` 내비게이션을 공유한다.
2. **폼(입력) 구조** — 추천 폼의 각 칸에는 `id="role"`, `id="skills"`, `id="top_n"` 같은 식별자가 붙어 있다. JavaScript는 **레이블이 아니라 `id`로 요소를 찾는다** (`document.getElementById("role")`).
3. **결과와 상태 표시 영역을 미리 비워 둠** — `#results`, `#loading-section`, `#form-alert`, `#ai-badge` 가 HTML에 이미 있고, 처음엔 `hidden` 상태다. JavaScript는 나중에 이 영역의 `hidden` 속성만 뒤집는다.

> **왜 처음부터 HTML에 넣어 두었나**
> 빈 `<div id="results"></div>` 을 JavaScript가 새로 만들면 되긴 하지만, 그러면 "결과가 나올 자리"가 코드 속에 숨어 있어 구조 파악이 어렵다. 반대로 HTML에 명시해 두면 **화면 구조는 HTML 파일만 읽어도 전부 파악**되고, JavaScript는 그 위에 값을 채워 넣는 역할에 집중한다.

`hidden` 속성 하나에 별도 CSS 규칙 없이도 요소가 사라지는 것, `role="alert"` 로 읽어 주는 화면 낭독기까지 함께 쓴 건 accessibility 때문이다. 비주얼만 예쁜 화면이 아니라 **키보드·스크린리더까지 고려한 구조**를 HTML 단계에서 결정한 것이다.

### CSS — 모양을 한 곳에 모아 두는 것

CSS는 `public/css/style.css` **한 파일**에 478줄을 모아 4개 페이지가 공유한다. 페이지마다 스타일 파일을 따로 두지 않은 이유는, 같은 버튼이 페이지마다 다른 모양이면 사용자 입장에서 inconsistently(일관성 없이) 느껴지기 때문이다.

이 CSS가 실제로 처리하는 것들:

- **색상 변수** — `:root` 에 `--accent`, `--border`, `--warn` 등을 정의해 두면, AI 분석 결과인지 코드 점수 결과인지 색 하나로 구분된다 (`ai-note` / `ai-note--off`).
- **반응형** — `1280×900` 에서 카드 3열, `390×844` 모바일에서 1열로 접힌다. 미디어 쿼리가 CSS 에 있고, **JavaScript 는 창 크기에 대해 아무것도 하지 않는다.** 화면 크기에 따라 모양이 바뀌는 것은 순전히 CSS 의 몫이다.
- **모션/접근성** — `prefers-reduced-motion` 을 존중하고, `:focus-visible` 로 키보드 포커스를 표시한다. 이 역시 CSS 만의 일이다.

### JavaScript — 동작과 통신

JavaScript는 사람이 "추천 받기"를 눌렀을 때 **비로소 일이 시작**된다. 이 프로젝트에서 JS 는 세 갈래로 나뉜다.

| 파일 | 책임 |
| --- | --- |
| `public/js/common.js` | 공통 유틸. 카드 렌더링(`renderJobCard`), 날짜 포맷, **`escapeHtml()` XSS 방어** |
| `public/js/api.js` | **서버 통신 전담.** `fetch` 래퍼 + 타임아웃 + 오류 메시지 한국어화 |
| `public/js/recommend.js` | 추천 페이지의 입력→요청→렌더링 오케스트레이션 |

**역할을 나눈 이유**: `api.js` 한 곳에 통신을 모았기 때문에, 타임아웃을 20초에서 45초로 바꿔야 할 때 `public/js/api.js` 한 군데만 고치면 된다. 만약 `recommend.js` 와 `jobs.js` 에 각각 `fetch` 를 썼다면, 동일한 오류 메시지 처리가 페이지마다 중복되고 한쪽만 고쳐지는 사고가 난다. 이건 과제 요구사항인 "코드 분리" 를 실제로 체감한 지점이다.

### 이 항목에서 배운 것

> **HTML은 "무엇이 있는가", CSS는 "어떻게 보이는가", JS는 "어떻게 반응하는가"를 결정한다.**
> 이 분리 덕분에 과제에서 하나를 고쳤을 때 다른 둘이 깨지지 않는다.
> 반응형은 JS가 아니라 CSS의 책임이고, 화면에 데이터를 채우는 것은 JS의 책임이며,
> 그 결과물 구조를 담는 자리는 HTML 이다.

## 2. 사용자 입력이 fetch 로 바뀌고 응답이 화면에 반영되는 흐름

### 전체 흐름 한 장

```
사용자가 "추천 받기" 클릭
  ↓
[recommend.js] handleSubmit(event)
  ↓ readProfile()        → 폼 6개 값을 JS 객체로 모음
  ↓ validate(profile)    → 빈 값이면 여기서 중단 (서버에 보내지 않음)
  ↓ showLoading()        → 버튼 비활성화 + 스켈레톤 표시
  ↓
[api.js] fetchRecommendations(profile)
  ↓ JSON.stringify(profile) → POST /api/recommend  (API_BASE = "")
  ↓
  ── 브라우저 → 네트워크 ──
  ↓
[api/recommend.py] handler.do_POST()
  ↓ _Request(self)  : BaseHTTPRequestHandler → _run() 이 기대하는 형태로 변환
  ↓ _run(request)   : 5단계 파이프라인
  ↓   1) 입력 검증      → 400 / 405
  ↓   2) 공고 수집/캐시  → 실패 시 503
  ↓   3) 코드 사전 필터  → 후보 8건, 0건이면 404
  ↓   4) AI 판정         → 실패해도 중단하지 않음
  ↓   5) 응답 조립       → 200 JSON
  ↓
[api.js] fetch 가 JSON 으로 파싱 → 상태 코드 확인 → 한국어 메시지로 변환 or 그대로 반환
  ↓
[recommend.js] updateAiBadge(data.ai_status)   → "AI 분석 적용됨" 등 배지 갱신
  ↓ renderResults(data)                        → resultsBox.innerHTML 에 카드 렌더링
  ↓ showResults()                              → 결과 영역 표시
  ↓ store.set(...)                             → 다음 방문을 위해 조건 저장
```

### 각 단계에서 "누가 무슨 일을 하는가"

#### ① 입력을 다루는 자: `readProfile()`

```js
function readProfile() {
  return {
    role: document.getElementById("role").value,
    skills: document.getElementById("skills").value,
    ...
  };
}
```

HTML의 `id` 를 이용해 폼 값을 **JS 객체 하나**로 모은다. 이 순간 사용자의 입력은 "문자열"이었고, 여기서부터는 요청에 실릴 **데이터**가 된다. 폼은 여러 개지만 서버가 받는 요청은 하나라는 사실이 이 함수에서 드러난다.

#### ② 보내기 전에 한 번 막는다: `validate()`

서버도 같은 검사를 한다(`recommend.py` 의 빈 입력 검사). **그러면서도 프론트에도 둔 이유**는 사용자 경험이다. 빈 칸인데 0.4초 왕복을 하고 나서 "입력해 주세요" 를 받는 것보다, 즉시 빨간 테두리와 안내를 보여주는 것이 낫다. 이건 중복이 아니라 **UX 계층과 검증 계층의 분리**다.

#### ③ 통신은 한 곳에서만: `api.js` 의 `request()`

```js
const response = await fetch(API_BASE + path, {
  method: options.method || "GET",
  headers: { "Content-Type": "application/json", Accept: "application/json" },
  body: options.body ? JSON.stringify(options.body) : undefined,
  signal: controller.signal,
});
```

`API_BASE = ""` 인 게 핵심이다. 브라우저는 **같은 도메인의 `/api/...` 만 호출**한다. 그래서 배포 주소가 `jobfit-seven.vercel.app` 로 바뀌어도 프론트 코드를 수정할 필요가 없다. 개발할 때는 로컬 서버가, 배포하면 Vercel 이 같은 경로를 제공할 뿐이다.

**타임아웃 처리가 실제로 하는 일**: `fetch` 는 기본적으로 시간이 지나도 요청을 취소하지 않는다. 사용자 입장에서 스피너만 무한히 돌게 되는 상황을 막으려고 `AbortController` 로 제한 시간을 강제한다.

```js
const controller = new AbortController();
const timerId = setTimeout(() => controller.abort(), timeout);
...
if (error.name === "AbortError") {
  // "응답이 너무 오래 걸려 요청을 중단했습니다" 라는 다른 메시지를 띄운다
}
```

AI 호출이 포함된 추천 요청에만 `timeout: 45000` 을 주어, 다른 요청(20초)보다 여유를 둔다. 요청마다 필요한 시간이 다르므로 **호출하는 쪽에서 그 요청의 성격을 알려주는 구조**로 설계했다.

#### ④ 응답이 조용히 흘러오지 않게 막는다: `if (!response.ok)`

`fetch` 는 404 나 500 에도 **reject 되지 않는다**. HTTP 오류는 "성공적으로 응답을 받았는데 그 내용이 오류"인 것이다. 그래서 `!response.ok` 를 별도로 확인해야 한다.

```js
if (!response.ok) {
  const error = new Error(describeError(response.status, payload));
  error.status = response.status;
  throw error;
}
```

또한 `response.json()` 자체가 실패할 수 있으므로(HTML 에러 페이지가 오는 경우) try/catch로 감싸 `payload = null` 로 처리한다. **"파싱에 실패했다"는 상태를 하나의 정상 흐름으로 취급**한 것이다.

#### ⑤ 화면에 반영한다: `renderResults()`

```js
resultsBox.innerHTML = results.map((item) => { ... }).join("");
```

여기서 XSS 방어가 필수다. 공고 제목·회사는 **외부 API 에서 온 문자열**인데, 이스케이프 없이 `innerHTML` 에 넣으면 `<script>` 같은 문자열이 실행될 수 있다. 그래서 모든 삽입에 `escapeHtml()` 을 건다.

```js
'<h3 class="job-card__title">' + escapeHtml(job.title) + '</h3>'
```

`escapeHtml()` 이 없다면 아무 데나 넣었다는 것만으로도 스크립트 실행이 가능해진다.

#### ⑥ 항상 처음으로 돌아간다: `finally`

```js
} finally {
  submitBtn.disabled = false;
  submitBtn.textContent = "추천 받기";
}
```

성공이든 실패든 **버튼 상태를 반드시 복구**한다. 이 한 줄이 없으면 한 번 실패한 뒤로 버튼이 영영 눌리지 않는 화면이 된다. 비동기 흐름에서 "성공 경로에서만 복구하는 코드"는 버그를 만든다.

### 이 항목에서 배운 것

> **사용자 입력은 폼에서 "JS 객체"가 되고, `JSON.stringify` 를 거쳐 네트워크를 건너 JSON 이 되고, 서버에서 다시 파싱된 "dict" 가 되고, 응답은 다시 JSON 문자열이 되어 돌아와 `innerHTML` 에 들어간다.**
> 이 변환 경로의 어느 지점에서든 "형식이 다르면 조용히 실패"할 수 있고, 그래서 4번의 `!response.ok` 확인과 5번의 이스케이프가 필수다.

## 3. Vercel Serverless Functions 란 무엇인가, 프론트가 백엔드를 부르는 구조

### Serverless Function 을 한 문장으로

> **서버를 미리 띄워 두지 않고, 요청이 들어올 때만 코드를 잠깐 실행해 응답을 돌려주는 방식이다.**
> 이 프로젝트는 그 실행 환경으로 **Vercel** 을 쓴다.

전통적인 서버는 항상 켜져 있고 요청을 기다린다. Serverless 는 코드를 저장해 두었다가 요청이 올 때 실행한다. 그래서 이 프로젝트에는 **서버 설정 파일도, 포트 관리도, 서버를 계속 켜 두는 비용도 없다.**

### 이 프로젝트의 구조: 두 영역이 배포물 하나에 나뉜다

```
사용자가 https://jobfit-seven.vercel.app/recommend 접속
   │
   ├── 정적 영역 (public/)
   │     └── recommend.html + style.css + *.js  → CDN 이 파일을 그대로 내려준다
   │
   └── 함수 영역 (api/)
         ├── /api/jobs      ← GET  엔드포인트
         └── /api/recommend ← POST 엔드포인트
```

Vercel 은 이 구조를 **폴더 이름으로 구분해서 자동으로 인식**한다.

- `api/` 아래의 `.py` 파일 → 각각 하나의 서버리스 함수(= URL)
- `public/` 아래의 파일 → 정적 파일

그래서 이 프로젝트의 `api/` 폴더 이름과 `public/` 폴더 이름은 **약속**이다. 임의로 이름을 바꾸면 엔드포인트가 사라진다.

### 엔드포인트는 "함수"처럼 보이지만 실제로는 HTTP 서버다

`api/recommend.py` 맨 아래를 보면 이런 형태다.

```python
class handler(BaseHTTPRequestHandler):   # noqa: N801 (Vercel 이 요구하는 이름)
    protocol_version = "HTTP/1.1"

    def do_POST(self):
        result = _run(_Request(self))
        ...
        self.send_response(result["statusCode"])
        ...
```

이름이 `handler` 이고 `_run()` 이라는 함수가 있어서 "함수를 호출하면 끝"으로 보이지만, 실제로는 **파이썬 표준 라이브러리 `BaseHTTPRequestHandler` 를 상속한 HTTP 서버**다. Vercel 이 이 클래스를 띄우고 요청이 올 때마다 `do_POST` 를 부른다.

이 구조는 **하나의 결정에서 두 가지 이득**을 만들어 낸다.

1. **진입점과 실제 로직을 분리했다.** `_run(request)` 은 HTTP 를 모른다. 입력만 받아 결과를 돌려줄 뿐이다.
2. **그래서 로컬에서 그대로 재사용할 수 있다.** [dev_server.py](../dev_server.py) 가 `_FakeRequest` 라는 가짜 request 객체를 만들어 `_run()` 을 직접 부른다. 배포 환경과 **동일한 로직**을 로컬에서 돌릴 수 있다. 로컬만 되는 테스트용 분기가 생기지 않는다.

> **실제로 겪은 문제 — 이 구조를 모르고 처음에 이렇게 썼다**
> `def handler(request):` 처럼 **일반 함수 형태**로 작성했다. 문법 오류가 아니어서 빌드도 통과했는데, 실제 URL에 접근하면 **404** 가 났다. 조용히 무시된 것이다.
> Vercel 파이썬 런타임은 진입점으로 `app` / `application` / **`BaseHTTPRequestHandler` 서브클래스** 형태를 요구하는데, 일반 함수는 아무 후보에도 해당하지 않았다. "코드를 실행했는데 404" 라는, 원인이 드러나지 않는 상태였다.

### 프론트에서 백엔드를 부르는 구조

**CORS 설정도, 도메인 설정도 없다.** 그 이유는 단순하다.

```js
const API_BASE = "";   // 같은 도메인의 /api 를 쓴다. 배포 시 자동 매칭된다.
```

브라우저가 `jobfit-seven.vercel.app` 의 페이지를 열면, 상대 경로 `/api/recommend` 는 **자동으로 같은 도메인**을 탄다. 페이지와 API가 같은 도메인에 있으므로 브라우저가 차단할 이유가 없다. CORS 에러를 만나지 않은 이유이며, 별도 처리가 필요 없었던 이유다.

만약 프론트와 백엔드가 다른 도메인(예: `api.example.com`)이었다면, 그때는 백엔드가 CORS 헤더를 명시적으로 내려줘야 한다. 이 프로젝트는 그 복잡함을 피하는 구조를 선택한 것이다.

### AI 키는 브라우저로 나가지 않는다

이 구조에서 가장 중요한 보안 성질이 하나 더 있다.

```
사용자 브라우저  →  jobfit-seven.vercel.app/api/recommend  →  서버(Python)  →  Gemini API
                   ←──────────── JSON (키 없음) ────────────────────────────
```

API 키는 **서버에서만** 읽는다(`ai.py` 의 `get_api_key()`). 브라우저는 `/api/recommend` 라는 URL만 알고 있을 뿐, 키가 무엇인지 모른다. 누군자가 개발자 도구(F12)에서 아무리 들여다봐도 키는 나오지 않는다. 키가 필요 없는 건 우연이 아니라, **키를 쓸 수 있는 유일한 위치가 서버라는 구조 때문**이다. 이 부분은 4번 항목에서 더 깊이 다룬다.

### 이 항목에서 배운 것

> **`api/` 아래 파일은 URL 이 되고, 각 파일은 HTTP 서버로 부팅된다.**
> 로직을 `_run()` 으로 분리하면 같은 코드를 로컬 개발 서버가 그대로 재사용할 수 있어,
> "배포에서만 나는 버그"의 상당 부분을 로컬에서 먼저 잡을 수 있게 된다.

## 4. API 키를 환경 변수로 관리해야 하는 이유

### 문제의 출발점: 키가 저장소에 들어가면 끝난다

API 키는 비밀번호이자 **결제 수단**이다. 이 프로젝트의 키는 Google Gemini 키이고, 새 프로젝트 발급 정책상 1개 계정에 1개만 존재한다. 그 키가 새면:

- 남의 사용자가 그 키로 요청을 보내고, **과금은 내 계정에서**
- 키가 회수될 때까지 내가 통제할 수 없다
- 저장소가 공개 저장소(`sayknow/A1-3`, PUBLIC)이므로 **누구나 `git log` 를 뒤질 수 있다**

키를 커밋했다면 **지우기 전까지는 유출된 상태**다. `git log` 에는 과거 커밋이 남아 있고, forks 를 따라갈 수 있다. 그래서 GitHub는 비밀키 스캐너를 넣었다.

### 이 프로젝트가 실제로 택한 방법

**(1) 키는 오직 `os.environ` 으로만 읽는다** — `api/_lib/ai.py`

```python
def get_api_key():
    """환경변수에서 API 키를 읽는다. 없으면 빈 문자열."""
    spec = PROVIDERS[active_provider_name()]
    return os.environ.get(spec["key_env"], "").strip()
```

코드 전체를 훑어도 키가 하드코딩된 곳이 없다. `GEMINI_API_KEY` 라는 **이름만** 있고 값은 없다.

**(2) 키 파일은 커밋 대상에서 제외한다** — `.gitignore`

```
.env
.env.local
.env.*.local
.vercel
*.key
secrets*.json
```

아예 **정규식으로 막아뒀다.** 실수로 `my_key.txt` 같은 이름으로 저장하는 경우까지 막으려고 한 것이다. 파일 하나만 막아두면 "아 이 이름은 안 되겠네" 하고 다른 이름으로 저장하는 사고가 나기 때문이다.

**(3) 예시 파일만 커밋한다** — `.env.example`

값 대신 **무엇을 넣어야 하는지 설명만** 적어 둔다. 이 덕분에 다른 사람이 이 프로젝트를 따라 할 때 필요한 정보를 잃지 않는다.

```
AI_PROVIDER=gemini
GEMINI_API_KEY=여기에_실제_키를_입력하세요
GEMINI_MODEL=gemini-3.5-flash-lite
```

**(4) 로그에서도 키를 마스킹한다** — `ai.py` 의 `_read_error_body()`

AI 호출이 실패하면 provider 가 준 오류 본문을 로그에 남기는데, **그 본문에 키가 되비쳐 나올 수 있다.** 그래서 마스킹한다.

```python
detail = " ".join(str(detail).split())[:limit]
return detail.replace(key, "***") if key else detail
```

"서버 밖으로만 유출되지 않으면 된다"는 사고가 흔한 곳이 **로그**다. 로그에 남은 키는 Vercel 대시보드에서 아무나 볼 수 있다. 그래서 키가 들어갈 수 있는 경로를 하나씩 막았다.

**(5) 화면에 키 정보를 내보내지 않는다** — `ai.py` 의 `describe()`

```python
def describe():
    return {"provider": name, "label": ..., "model": get_model(), "configured": bool(get_api_key())}
```

응답 JSON 에는 **키가 설정되어 있는지만** `configured: true/false` 로 들어간다. 값은 절대 포함되지 않는다. 화면의 "AI 분석 적용됨" 배지 판정은 이 `configured` 값으로 이뤄진다. 즉 **키 없이도 UI가 필요한 정보를 얻는다.**

### 환경변수 구조가 만들어 낸 유연성

`ai.py` 의 `PROVIDERS` 레지스트리는 **키 등록부**라기보다 **연결 설정표**에 가깝다.

```python
PROVIDERS = {
    "gemini": {"label": "Google Gemini", "key_env": "GEMINI_API_KEY", ...},
    "openai":  {"label": "OpenAI",        "key_env": "OPENAI_API_KEY", ...},
}
```

| 바꿈 | 방법 | 코드 수정 |
| --- | --- | --- |
| 모델 변경 | `GEMINI_MODEL` 값만 변경 | 없음 |
| 제공사 전환 | `AI_PROVIDER=openai` | 없음 |
| 키 교체 | 대시보드에서 값만 변경 | 없음 |

`api/recommend.py` 는 provider 이름을 **모른다**. `ai.recommend()` 만 부를 뿐이다. 그래서 키를 다른 회사로 옮겨도 코드가 바뀌지 않는다.

### 키가 없을 때: 죽지 않는 구조

환경변수 기반 설계의 진짜 가치는 여기서 드러난다. **키는 선택 사항**으로 두었다.

```python
if ai.is_available():
    ai_verdicts = ai.recommend(profile, candidates)
    ...
```

키가 없으면 AI 호출을 건너뛰고, 코드 점수로 계산한 결과를 **그대로 반환한다**. 화면에는 "AI 미연동 상태" 배지가 뜬다. `ai_status` 필드가 `disabled` / `failed` / `ok` 세 값을 전달하고, `updateAiBadge()` 가 그것을 사람이 읽는 문구로 바꾼다.

> **보안 설계가 곧 UX 설계가 된 지점**
> "키가 없어서 실패했습니다"와 "키가 없어서 AI 기능을 끄고 키워드 매칭만 표시합니다"는 전혀 다른 메시지다.
> 전자는 결함이고, 후자는 **의도된 폴백**이다. `ai_status` 필드가 그 구분을 운반한다.

### Vercel 에서 설정하는 법

1. 대시보드 → 프로젝트 → **Settings** → **Environment Variables**
2. `AI_PROVIDER=gemini`, `GEMINI_API_KEY=<실제값>` 추가 (Production / Preview / Development 체크)
3. **Redeploy** ← 이 단계를 빠뜨리면 안 된다

**3번이 반드시 필요한 이유**: 환경변수는 **빌드 시점에 주입**된다. 이미 올라간 배포물에는 이전 빌드의 값이 박혀 있다. 대시보드에 변수를 추가해도 **Redeploy 하지 않으면 그 값은 반영되지 않는다.** 이건 5번 항목에서 더 자세히 다룬다.

### 이 항목에서 배운 것

> **키를 코드에 적으면 저장소에 남고, 저장소는 공개되므로 키는 유출된다.**
> 환경변수는 "서버에서만 읽히는 값"을 넣을 수 있는 수단이고, 이는 **서버만 키를 아는 구조를 가능하게 만든다.**
> 그래서 환경변수는 보안 수단인 동시에, **키가 없어도 서비스가 돌아가는 유연성**까지 함께 얻는다.

## 5. 로컬 환경과 배포 환경의 차이, 그리고 수정 → 재배포 흐름

### 같은 코드가 다른 곳에서 돌아간다

로컬에서는 `python3 dev_server.py` 로, 배포에서는 Vercel 이 자동으로 띄운다. **같은 `_run()` 로직을 공유**하지만 그 바깥은 전혀 다르다.

| | 로컬 | Vercel 배포 |
| --- | --- | --- |
| 서버 | `dev_server.py` 직접 실행 | 플랫폼이 요청마다 기동 |
| 진입점 | 내가 만든 `Handler` | Vercel 규약(`handler`) |
| 정적 파일 | 직접 읽어 응답 | CDN 이 서빙 |
| 파일 경로 | 내 컴퓨터의 실제 경로 | `/var/task/api/...` (읽기 전용) |
| 실행 시간 | 제한 없음 | 함수 타임아웃 존재 |
| 환경변수 | 내 셸 / `.env.local` | 대시보드에서 등록 (빌드 시점 주입) |
| 메모리 캐시 | 프로세스 동안 유지 | 인스턴스가 살아 있는 동안만 유지 |
| 로그 | 터미널에 바로 출력 | Vercel 대시보드 Logs |

로컬 개발 서버의 핵심은 이 두 줄이다.

```python
from api.jobs import _run as jobs_run
from api.recommend import _run as recommend_run
```

**엔드포인트의 진짜 로직을 직접 import 해 부른다.** 그래서 로컬과 배포가 같은 로직을 실행한다.

### 실제로 드러난 차이 4가지

로컬에서 아무 문제가 없던 코드가 배포에서만 깨졌다. 각 사례는 **무엇이 달랐는지** 설명할 수 있었다.

#### 사례 1 — 진입점 형태가 다르면 조용히 404

로컬에서는 `_run()` 을 직접 부르므로 `def handler(request):` 로 써도 아무 문제가 없었다. 로컬에서 100% 동작하는 코드였다.

배포에서 404. **차이는 로컬 서버가 Vercel 의 규약을 지킨다는 보장도, 강제도 하지 않았기 때문**이다. 로컬이 더 느슨했던 것이다.

#### 사례 2 — 파일 경로가 다르면 모듈을 못 찾는다

`_lib` 패키지는 `api/` 옆에 있으므로, 그 폴더를 경로에 넣어야 한다.

```python
API_DIR = os.path.dirname(os.path.abspath(__file__))
if API_DIR not in sys.path:
    sys.path.insert(0, API_DIR)
```

내 컴퓨터에서는 프로젝트 루트를 넣어도 동작했다. 그런데 Vercel 은 이 파일을 **`/var/task/api/jobs.py` 로 복사해 실행한다.** 루트에 `api/` 가 없어 `_lib` 을 찾지 못하고 500이 났다.

> **원인을 말로 설명하는 문장**: "내 파일 기준으로는 폴더가 항상 옆에 있으므로 절대경로를 뽑으면 위치와 무관하게 동작할 줄 알았는데, Vercel 은 실행 시점에 파일을 다른 위치에 복사해 두기 때문에, 배포 환경의 경로 구조를 전제로 하지 않은 코드가 깨졌다."

#### 사례 3 — 설정 파일이 자동 인식을 방해했다

`vercel.json` 에 `outputDirectory` 를 명시하자 **`/api/*` 가 404** 가 되었다. 설정을 추가했는데 동작이 깨졌다.

원인은 **Vercel 이 "빌드 출력이 지정된 디렉터리" 모드로 전환하면서 `api/` 를 정적 자산으로 취급**했기 때문이다. 설정이 자동 인식을 대체했다. 최종적으로 **`vercel.json` 을 두지 않는 zero-config** 가 정답이었다. 파일이 없는 것이 더 나은 구조인 경우였다.

프레임워크 프리셋도 마찬가지였다. `Python` 으로 지정하면 Vercel 이 단일 엔트리포인트(`app.py` 등)를 찾으려 해 `api/` 아래 여러 엔드포인트 구조와 맞지 않았다. `Other` 가 맞았다.

#### 사례 4 — 환경변수는 배포마다 다시 주입된다

대시보드에 `GEMINI_API_KEY` 를 등록하고 화면을 새로고침했는데 **여전히 `ai_status: "disabled"`** 였다.

로컬에서는 `.env.local` 에 적으면 즉시 반영되지만, Vercel 환경변수는 **빌드 시점에 주입**된다. 이미 올라간 배포물에는 이전 빌드의 값이 박혀 있으므로, **Redeploy 가 필요**하다. 환경변수를 "적용"하는 것이 아니라 "적용된 상태로 다시 빌드"해야 하는 것이다.

### 수정 → 재배포 흐름

```
① 증상 파악 (사용자가 본 화면 / 상태 코드)
        ↓
② Vercel Logs 확인  ── 서버에 뭐가 찍혔는지가 원인 후보 목록을 좁혀 준다
        ↓
③ git status 로 작업 트리 확인 → 내가 만든 파일만 스테이징
        ↓
④ 커밋 (왜 고쳤는지가 메시지에 들어간다)
        ↓
⑤ git push  ──▶  Vercel 자동 감지 → 새 빌드 → 새 배포
        ↓
⑥ 실제 배포 주소에서 재검증 (로컬이 아니라 배포 URL 로)
        ↓
⑦ 해결 안 되면 ②로 돌아감
```

이 순서에서 **핵심은 ⑥이 로컬 검증이 아니라는 점**이다. 사례 1~4는 전부 로컬에서는 정상이었고, 실제 배포 URL 에서만 드러났다. 그래서 배포 후에는 반드시 **실제 주소로 같은 요청을 다시 보내 상태 코드를 확인**한다. 이 프로젝트에서 실제로 한 검증이 아래 표다.

| 요청 | 실측 응답 |
| --- | --- |
| `GET /api/jobs?limit=100` | 200 · 135건 |
| `POST /api/recommend` (정상 입력) | 200 · AI 재랭킹 반영 |
| `GET /api/jobs?limit=abc` | 400 |
| `GET /api/jobs?limit=9999` | 400 |
| `GET /api/recommend` | 405 |
| `POST /api/recommend` (빈 본문) | 400 |
| `POST /api/recommend` (깨진 JSON) | 400 |
| `GET /api/nope` | 404 |

이 표가 있는 이유: **"수정했다"는 주장과 "수정됐다"는 증거는 다르다.** 400/405/404 경계까지 실측해야 "실패 처리"라는 요구사항이 실제로 충족됐음을 말할 수 있다.

### 배포 후 문제 수정에 대한 원칙

1. **재현 가능한 형태로 기록한다.** "뭔가 안 된다"가 아니라 "`GET /api/recommend` 가 404"처럼 상태 코드와 URL 을 함께 적는다.
2. **Logs 를 본다.** 화면만 보면 "AI가 안 된다"까지밖에 모른다. 서버 로그에는 provider 가 준 정확한 사유가 있다.
3. **추측으로 수정하지 않는다.** 사례 4에서 "설정이 안 됐나?" 하고 키를 다시 등록하는 건 시간 낭비였다. Logs 를 보니 빌드 시점 주입 문제였음이 보였다.
4. **수정은 작게, 검증은 크게.** 한 번에 하나만 고치고 배포해서, 다른 것이 망가지지 않았는지 함께 확인한다.

### 이 항목에서 배운 것

> **로컬이 더 느슨할 때가 있다.** 로컬 개발 서버는 플랫폼 규약을 강제하지 않으므로,
> 규약 위반(진입점 형태, 절대경로 전제)이 로컬에서는 정상으로 보인다.
> 그래서 **배포 후 실제 URL 로 재검증하는 과정이 반드시 있어야 하고**,
> 환경변수처럼 **적용 시점**이 존재하는 설정은 "등록"과 "반영"이 다르다는 점을 기억해야 한다.

## 6. AI 코딩 도구로 코드를 만들어도, 오류 원인을 설명할 수 있는가

이 항목은 서술이 아니라 **증거**다. AI 도구(Freebuff Desktop)와의 대화에서 실제로 발생한 문제를 원인과 해결 방향까지 함께 기록한다.

### 에피소드 A — 서버는 성공했는데 기능은 조용히 죽어 있었다

**겉으로 보이는 것**: API 응답이 200. `ai_status` 도 `"ok"`. 하지만 결과의 `ai_used` 가 **전부 false** 였다. AI가 분석한 것 같은데 실제론 아무것도 적용되지 않은 상태였다.

**진단 과정**:

1. "HTTP 200인데 왜 AI 결과가 안 나오지?" 라는 질문에서 출발했다. **에러가 아니라 조용한 실패**는 가장 찾기 어렵다.
2. 응답을 뜯어보니 AI가 돌려준 `id` 와 서버가 가진 공고 `id` 가 **한 건도 겹치지 않았다.**
3. 프롬프트를 다시 읽었다. 지시문에는 "id를 그대로 복사하라"고 적혀 있었다. 그런데 **후보 목록 블록에 id가 아예 없었다.**
   ```python
   "[{index}] id: {job_id}\n"     # ← 이 줄이 없었다
       "    제목: {title}\n"
   ```
   모델에게 없는 값을 복사하라고 한 셈이므로, 임의의 값을 지어낼 수밖에 없었다.

**수정 방향** — 두 겹으로 막았다.

- 근본 수정: 후보 블록에 `[n] id: {job_id}` 를 넣어 **복사할 대상을 제공**한다.
- 안전망: `_parse_ai_json(content, expected_ids)` 에 순서 대응 로직을 추가한다. 개수까지 맞으면 순번으로 대응시킨다.
- 관찰 가능성: `[ai] matched N/M` 로그를 남겨 **몇 건이 매칭됐는지 항상 보이게** 한다.

> **왜 이게 더 중요하냐면**
> `ai_status: "ok"` 는 "provider 가 200을 돌려줬다"는 뜻일 뿐,
> "응답이 실제로 반영됐다"는 뜻이 아니다.
> 이 두 상태를 분리해서 보여줄 로그가 없었다면, 이 버그는 **끝까지 발견되지 않았을 것**이다.

### 에피소드 B — 로그에 상태 코드만 남기면 원인을 구분할 수 없다

**겉으로 보이는 것**: AI 호출이 실패하는데 로그에 `HTTP 403` 만 있었다. 403이 **무슨 의미인지** 알 수 없었다.

가능성은 여러 개였다: 키가 폐기됐거나 / API가 꺼져있거나 / 할당량 초과. **같은 403 안에서 원인이 갈린다.**

**수정 방향**: 에러 응답 본문을 읽어서 provider 가 알려준 사유를 그대로 로그에 남겼다.

```python
detail = " ".join(str(detail).split())[:limit]
return detail.replace(key, "***") if key else detail
```

그 결과 실제 메시지가 이런 형태로 드러났다:

```
[ai] gemini HTTPError 503 UNAVAILABLE / This model is currently experiencing high demand
```

"키가 잘못된 게 아니라 **그 모델이 혼잡하다**"가 드러나고, **수정 방향이 즉시 결정된다.** 재시도가 답이었다. 상태 코드만으로는 이 결론에 도달할 수 없다.

같은 로그가 키 문제도 구분해 줬다: `401 UNAUTHENTICATED` 는 키 오류, `400 INVALID_ARGUMENT` 는 모델명 오류, `403 PERMISSION_DENIED` 는 API 비활성화. **같은 코드로 전혀 다른 원인이 들어온다.**

### 에피소드 C — 원인에 맞게 모델을 고르는 것

에피소드 B의 로그를 보고 보니 `gemini-3.8-flash` 가 혼잡할 때 503을 던졌다. 그래서:

1. **기본 모델을 더 가벼운 모델로 낮췄다** (`gemini-3.5-flash-lite`).
2. **일시적 오류에만 짧게 재시도**하도록 했다 (`RETRY_STATUS = (429, 500, 502, 503, 504)`).
3. **재시도해도 실패하면 그대로 폴백** — 사용자는 AI 실패를 모르고 코드 점수 결과를 받는다.

중요한 점은 **재시도가 인증 실패(401)에는 적용되지 않는다**는 것이다. 401 은 다시 시도해도 똑같으므로, 즉시 실패시켜 원인이 은폐되지 않게 했다.

### 에피소드 D — 입력 데이터가 생각과 다른 모양으로 온다

**겉으로 보이는 것**: 급여가 "90k - 105k" 인데 파싱하니 `105` 가 나왔다. `k` 단위를 놓쳤고, `"90k - 105k"` 문자열에서 숫자만 뽑은 탓이었다.

**원인**: 파서가 단위 표기와 유럽식 표기(`€45.000`)를 고려하지 않았다. **데이터는 내가 정한 형식이 아니라는 전제**가 문제였다.

**수정 방향**: 단위(`k`/`m`)와 유럽식 구분자 표기를 처리하는 로직을 추가했다. 방어적으로 생각하면 **외부 데이터의 형식을 먼저 가정하지 않는 것**이 같은 종류의 사고를 막는다.

### 에피소드 E — 화면이 멈추는 유형이 세 가지나 있다

에피소드와 함께 발견한 실패 처리들:

| 증상 | 원인 | 처리 |
| --- | --- | --- |
| `fetchJobs is not defined` | `index.html` 에 `api.js` 스크립트 태그 누락 | 스크립트 로드 추가 |
| 버튼이 눌리지 않음 | 실패 경로에서 버튼 복구 누락 | `finally` 로 이동 |
| 공고 0건 | 외부 API 전체 실패 | 503 + 안내, 빈 화면 아님 |
| 공고에 세차장 직군이 1위로 | 비-IT 공고가 섞임 | 직군 적합도 가중치로 감점 |
| 스피너가 무한 반복 | 타임아웃 미처리 | `AbortController` |

공통점이 있다. **모두 "사용자에게 무엇을 보여줄지"가 결정되지 않아서 생겼던 문제**였다. 그래서 각각의 실패 지점에 사람이 읽을 메시지를 붙였다.

### 이 문서가 말하려는 것

AI 코딩 도구는 **코드 초안을 빠르게 만들어준다.** 하지만 이 사례들처럼 다음은 스스로 해야 한다.

1. **"정상인데 틀린" 상태를 알아채는 것** — 에피소드 A 는 모든 상태가 초록이었다. 조용한 실패는 성공으로 보이는 실패다.
2. **로그가 원인을 말해주도록 만드는 것** — 에피소드 B. 상태 코드만으로는 원인을 구분할 수 없다.
3. **원인에 맞는 수정 방향을 고르는 것** — 401 과 503 은 같은 실패가 아니라 다른 실패다.
4. **사용자에게 보여줄 결과를 결정하는 것** — 실패해도 뭐가 보인다가 먼저 정하면, 코드는 그쪽으로 따라간다.

> **AI 가 코드를 만들면, 그다음은 "왜 이렇게 동작하는지"를 내가 설명할 수 있어야 한다.**
> 에피소드 A 는 `_run()` 이 id로 AI 판정을 연결한다는 사실,
> 에피소드 B 는 HTTP 상태 코드가 원인이 아니라는 사실,
> 사례 2 는 절대경로가 실행 위치에서 온다는 사실을 설명할 수 있어야 의미가 있다.
>
> 이 문서를 쓴다는 것 자체가 그 설명 능력의 증거다.
